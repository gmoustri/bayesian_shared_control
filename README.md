

# Bayesian Shared Control
## Assisted Teleoperation with Bayesian Intention Estimation

The `bayesian_shared_control` package provides intent-aware shared control for ROS 2 mobile-robot teleoperation. It uses motion clusters generated by the *Dynamic Window Arc-Line Planner* ([`dwal_planner`](https://github.com/gmoustri/dwal_planner)) to estimate the operator's intended direction, select a collision-aware path, and generate an assisted velocity command.

The package contains:

- the `shared_control_node` for Bayesian intention estimation and shared-control command generation;
- launch files and parameter profiles for local Gazebo testing and Summit XL deployment;
- joystick and keyboard teleoperation utilities;
- a browser-based teleoperation panel;
- a service-controlled ROS bag recorder; and
- RViz-compatible path and intention visualizations.

To use the controller, you must:

- have a mobile robot accepting velocity commands;
- have an odometry source;
- download, install and publish *near* and *far* motion clusters from `dwal_planner`; and
- publish the required TF transforms.

The package has been tested locally in a Gazebo simulation and on a Robotnik Summit XL mobile robot.

## Controller output

The `shared_control_node` publishes:

- the assisted robot velocity command on the topic configured by `output_cmd_topic`;
- the path corresponding to the operator's command on `/shared_controller/path_human`;
- the path selected by the shared controller on `/shared_controller/path_shared`; and
- Bayesian cluster-belief markers on `/shared_controller/intent_plot`.

## Bayesian intention estimation

The controller maintains a probability distribution over the motion clusters produced by `dwal_planner`. This belief is updated recursively using the operator's steering input and the temporal continuity of the available clusters. The most probable cluster is treated as the operator's intended motion region and is used to select the assisted path.

The complete Bayesian formulation and shared-control strategy are presented in the AIM 2026 paper linked above.

## Expected DWAL input

The controller consumes `dwal_planner/msg/ClusterGroup` messages. The implementation expects each usable cluster to provide:

- a persistent cluster `id`;
- a non-empty `paths` array;
- a horizon radius `r`;
- a starting pose `pose0 = [x, y, yaw]`; and
- for each path, an angle `phi` and integer navigation `cost`.

Path arrays are assumed to be ordered by `phi`, because the first and last paths are used as the cluster angular limits.

## Operator input

The controller accepts operator velocity commands through the topic configured by `user_cmd_topic`. The package provides three input methods.

### Browser gamepad input

This is the input method used in the Summit XL experiments. A PlayStation controller is paired with or connected to the device running the browser interface, such as the Meta Quest 3. The browser reads the controller through the JavaScript Gamepad API.

In the current web interface:

- **R1** enables motion;
-   **R2** bypasses the shared controller and reverts to (mostly) direct teleoperation. Used when robot is trapped or the DWAL does not compute any motion clusters e,g, in very cluttered environments;
- the **left-stick vertical axis** controls forward and reverse velocity;
- the **right-stick horizontal axis** controls angular velocity;
- `/cmd_vel_web` is published as `geometry_msgs/msg/Twist`; and
- `/joy_web` is published as `sensor_msgs/msg/Joy`.


The robot parameter profile sets:

```yaml
user_cmd_topic: "/cmd_vel_web"
joy_topic: "/joy_web"
```

The web commands are generated only while `teleop_panel_robot.html` is open, its JavaScript is running, and the page is connected to ROS 2 through `rosbridge`. Starting `teleop_servers_launch.py` alone does not publish `/cmd_vel_web` or `/joy_web`; it only starts the services required by the browser interface.

The HTML page does not have to be served by the included Python HTTP server. It may be served by another web server, provided that the page can connect to a running `rosbridge_websocket` instance.

The browser implementation is not inherently tied to the Meta Quest 3 or to a specific PlayStation controller. It can be used with another browser-capable device and a gamepad supported by the browser's Gamepad API, although button and axis mappings may need adjustment.

### ROS joystick input

For local operation, `joy_teleop.launch.py` starts `joy_node` and `teleop_twist_joy`. The generated velocity command is published to `/user_cmd`, which is the input topic used by the local Gazebo profile.

```bash
ros2 launch bayesian_shared_control joy_teleop.launch.py
```

### Keyboard input

The package also provides `teleop_keyboard.py` for local testing without a gamepad:

```bash
ros2 run bayesian_shared_control teleop_keyboard.py
```

## ROS interfaces

The launch files place the controller at `/shared_controller/shared_controller`.

### Subscribed topics

| Topic | Message type | Configuration |
|---|---|---|
| `/dwal_planner/clusters_near` | `dwal_planner/msg/ClusterGroup` | Fixed in the current implementation; best-effort, depth 1 |
| `/dwal_planner/clusters_far` | `dwal_planner/msg/ClusterGroup` | Fixed in the current implementation; best-effort, depth 1 |
| `user_cmd_topic` | `geometry_msgs/msg/TwistStamped` or `geometry_msgs/msg/Twist` | Selected by `use_stamped_twist_input` |
| `odom_topic` | `nav_msgs/msg/Odometry` | Supplies measured velocity and output frame |
| `joy_topic` | `sensor_msgs/msg/Joy` | Used for no-cluster pass-through control |

### Published topics

| Topic | Message type | Description |
|---|---|---|
| `output_cmd_topic` | `geometry_msgs/msg/TwistStamped` or `geometry_msgs/msg/Twist` | Shared-control command; type selected by `use_stamped_twist_output` |
| `/shared_controller/path_human` | `nav_msgs/msg/Path` | Path corresponding to the operator steering command |
| `/shared_controller/path_shared` | `nav_msgs/msg/Path` | Path selected by the shared controller |
| `/shared_controller/intent_plot` | `visualization_msgs/msg/MarkerArray` | Belief bars and MAP-cluster highlighting |

## `shared_control_node` parameters

The following values are supplied by `config/sc_params_robot.yaml` for deployment on the Summit XL robot.

- **`cluster_topic`** (`string`, value: `/dwal_planner/clusters_near`)

  Legacy/configuration field. The current code does **not** use it; near and far subscriptions are hard-coded.

- **`user_cmd_topic`** (`string`, value: `/cmd_vel_web`)

  Input user-command topic.

- **`output_cmd_topic`** (`string`, value: `/shared_control_teleop/cmd_vel`)

  Output shared-control command topic. The robot launch remaps this to `/robot/shared_control_teleop/cmd_vel`.

- **`odom_topic`** (`string`, value: `/Odometry`)

  Odometry input topic.

- **`joy_topic`** (`string`, value: `/joy_web`)

  Joystick input used to read the pass-through button.

- **`r2_button_index`** (`integer`, value: `7`)

  Zero-based index into `sensor_msgs/msg/Joy.buttons`.

- **`use_stamped_twist_input`** (`boolean`, value: `false`)

  Subscribe to `TwistStamped` when `true`; otherwise subscribe to `Twist`.

- **`use_stamped_twist_output`** (`boolean`, value: `false`)

  Publish `TwistStamped` when `true`; otherwise publish `Twist`.

- **`v_low`** (`double`, value: `0.30`)

  Lower robot-speed threshold for switching from far to near clusters, in m/s.

- **`v_high`** (`double`, value: `0.40`)

  Upper robot-speed threshold for switching from near to far clusters, in m/s.

- **`c_max`** (`double`, value: `255.0`)

  Cost-normalization denominator. Must be greater than zero.

- **`alpha`** (`double`, value: `0.4`)

  Intra-cluster path-scoring weight. Higher values emphasize agreement with user steering; lower values emphasize navigation cost. Valid range: `(0, 1]`. This is distinct from `intent.alpha`.

- **`s_min`** (`double`, value: `0.2`)

  Minimum linear-speed scaling applied by cost damping. Valid range: `(0, 1]`.

- **`Kphi`** (`double`, value: `1.0`)

  Gain converting user yaw rate to DWAL path angle. Must be greater than zero.

- **`Kmax`** (`double`, value: `4.0`)

  Maximum permitted curvature used to clamp the user path angle. Must be greater than zero and should match the corresponding DWAL planner setting.

- **`intent.alpha`** (`double`, value: `0.92`)

  Sticky transition probability retained by a cluster whose ID persists between updates. Intended range: `[0, 1]`.

- **`intent.beta`** (`double`, value: `8.0`)

  Sharpness of angular-distance-based prior redistribution. Larger values favour nearby cluster directions more strongly.

- **`intent.eta`** (`double`, value: `0.5`)

  Scale factor used to derive the split-normal likelihood widths from cluster span.

- **`intent.sigma_min`** (`double`, value: `0.03`)

  Minimum likelihood standard deviation, in radians.

- **`intent.min_confidence`** (`double`, value: `0.0`)

  Minimum MAP posterior required to accept a cluster. `0.0` disables confidence gating.

If `v_low >= v_high`, the node warns and resets both values to `0.25` and `0.35`.

## Supplied parameter profiles

- `config/sc_params_robot.yaml`: configuration used for deployment on the **Summit XL robot**, with unstamped command input/output, `/Odometry`, web command input, and robot shared-control output.
- `config/sc_params_local.yaml`: configuration used to test the controller locally in a **Gazebo simulation**, with stamped command input/output, `/odom`, `/user_cmd`, and local `/cmd_vel` output.

Override the robot profile with:

```bash
ros2 launch bayesian_shared_control controller_robot.launch.py \
  params_file:=/absolute/path/to/parameters.yaml
```

The launch argument `params_file` is a `string` containing the full parameter-file path.

## Joystick teleoperation parameters

- **`publish_stamped_twist`** (`boolean`, value: `true`)

  Publish `TwistStamped`.

- **`stamped_twist_frame`** (`string`, value: `base_link`)

  Frame ID used for stamped commands.

- **`require_enable_button`** (`boolean`, value: `true`)

  Require an enable button while commanding motion.

- **`enable_button`** (`integer`, value: `5`)

  Normal-speed enable button.

- **`enable_turbo_button`** (`integer`, value: `4`)

- **`axis_linear.x`** (`integer`, value: `1`)

  Joystick axis for forward/backward motion.

- **`scale_linear.x`** (`double`, value: `0.6`)

  Normal linear scale, in m/s.

- **`scale_linear_turbo.x`** (`double`, value: `1.2`)

  Turbo linear scale, in m/s.

- **`axis_angular.yaw`** (`integer`, value: `0`)

  Joystick axis for yaw.

- **`scale_angular.yaw`** (`double`, value: `1.8`)

  Normal angular scale, in rad/s.

- **`scale_angular_turbo.yaw`** (`double`, value: `2.5`)

  Turbo angular scale, in rad/s.

## Keyboard teleoperation

`scripts/teleop_keyboard.py` publishes keyboard commands to `cmd_vel`. At startup it queries the following parameters from `/dwal_planner/dwal_generator`:

- **`dwal_generator/max_trans_vel`** (`double` or `integer`, fallback: `0.5`)

- **`dwal_generator/max_vel_theta`** (`double` or `integer`, fallback: `1.0`)

- **`dwal_generator/acc_lim_x`** (`double` or `integer`, fallback: `1.0`)

- **`dwal_generator/acc_lim_th`** (`double` or `integer`, fallback: `1.0`)

The keyboard node has no declared ROS parameters. Its input polling period is hard-coded to `0.1 s`, and its linear and angular command increments are each hard-coded to `0.1`.

## Build

Place this package and `dwal_planner` in the same ROS 2 workspace, then install dependencies and build:

```bash
cd <workspace>
rosdep install --from-paths src --ignore-src -r -y
colcon build --symlink-install --packages-select bayesian_shared_control
source install/setup.bash
```

Core dependencies include `rclcpp`, `geometry_msgs`, `nav_msgs`, `sensor_msgs`, `visualization_msgs`, TF2, `nav2_costmap_2d`, Boost, Eigen, and the custom `dwal_planner` package.

Auxiliary launch files additionally require the relevant packages, including `joy`, `teleop_twist_joy`, `std_srvs`, `rosbridge_server`, and `web_video_server`.


### Web teleoperation services

Run the following launch file on the robot computer when using the browser-based teleoperation panel:

```bash
ros2 launch bayesian_shared_control teleop_servers_launch.py
```

The launch file starts four supporting processes:

- **`rosbridge_websocket` on port `9092`**

  Provides the WebSocket connection between the browser and ROS 2. The teleoperation panel uses this connection to publish commands, subscribe to robot-state and visualization topics, and call the recording services.

- **`web_video_server` on port `8080`**

  Converts the configured ROS camera topic into an MJPEG stream that can be displayed by the `<img>` element in the teleoperation panel.

- **Python HTTP server on port `8000`**

  Serves the HTML, JavaScript, and CSS files that implement the browser interface. The current launch file serves its working directory, so it should be launched from the directory containing the `html/` files, or modified to use that directory explicitly.

- **`remote_recorder.py`**

  Provides `/bag_record_start`, `/bag_record_stop`, and `/bag_record_delete_last`, allowing ROS bag recording to be controlled through the buttons in the web interface.

This launch file is required when the browser panel is used for remote teleoperation, camera display, ROS visualization, or browser-controlled bag recording. It is not required when commands are supplied by another ROS node, such as the keyboard or standard joystick teleoperation utilities.

The browser-based input path is described in [Operator input](#operator-input).

A typical startup sequence is:

1. Start the robot, the DWAL planner, and the shared-control controller.
2. Start `teleop_servers_launch.py` on the robot computer.
3. Pair or connect the PlayStation controller to the Meta Quest 3 or other browser device.
4. Open:

   ```text
   http://<robot-ip>:8000/teleop_panel_robot.html
   ```

5. Set the WebSocket address in the panel to:

   ```text
   ws://<robot-ip>:9092
   ```

6. Select **Connect** before operating the controller.

## Implementation notes

- `cluster_topic` is currently declared and shown in startup logging but does not control either cluster subscription.
- Near/far topic names and debug visualization topic names are currently absolute and hard-coded.
- `Kmax` should remain consistent with the DWAL planner's curvature configuration.
- The two parameters named `alpha` have different roles: `alpha` weights path cost versus user agreement, while `intent.alpha` controls temporal persistence in the Bayesian filter.
- The HTML assets are present in the source tree but are not installed by the current `CMakeLists.txt`.
